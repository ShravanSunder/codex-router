## Six closure questions and bounded candidate

1. **Admission job and answer receiver.** Prepare an answer channel before the first cancellable history mutation. Its receiver belongs to the stable adapter/turn actor; the shared broker owns the registration mutation and an independent admission acknowledgment. Loss of the acknowledgment observer does not drop that receiver. An ordinary caller that actually drops its only receiver keeps requesterUnavailable semantics. Native actor coverage must start at actor admission in the existing adapter holder tracker; relying solely on registry.shutdown transfer is insufficient because outer/lazy abort paths bypass it. No reader ownership moves into the broker or keeper.

2. **Resolution delivery then persistence.** The broker claims one decision, delivers the validated answer, then finishes history IO under its own tracked job even when the approver front door disappears. It never restores answer eligibility or resends after history failure. Runtime terminal facts need only request id/state; no additional answer journal is proposed. Current error/listing and cancellation failure behavior require explicit design closure so no path waits forever for a sender that was retained solely because history failed. Exact interfaces remain conditional; no new public result shape is assumed.

3. **Reader and full abort ownership.** The adapter retains native callback address, generation/thread/turn, admission and answer futures. Broker waits must leave the inline native reader; existing approval waits also need retained-future handling to satisfy RQ5 when another callback is pending, with their decisions/mapping preserved. Full outer/lazy/listener abort paths must retain the admitted actor through the existing adapter holder tracker or positively retire its actual native scope. Frontend EOF remains detachment. No caller-close token is silently renamed native retirement.

4. **Positive causes and native release.** Separate public approver action from internal resolution origin/cause. Only explicit approver cancellation uses the Question's exact-turn interrupt path. Native resolution, turn end, backend/provider retirement and actual unavailable receiver are positive lifecycle facts; frontend loss alone is not. Tagged native handling converts ordinary callback errors/receiver loss to empty answers, while its turn-transition error skips that conversion. Therefore lifecycle release cannot simply manufacture an RPC error, empty answer or dropped native callback. The native scope and actual cause must govern release; ordinary pending callbacks can survive client disconnect and replay.

5. **Fixed reversible E4 cut.** Separate question IO jobs from human-answer waiters. Pause new mutation admission through the existing E4 write barrier; finish/join already-admitted registration/resolution/history writers, without joining human waits. Refused handover preserves owners and resumes the barrier. Accepted release must preserve or positively retire actual receiver/callback ownership, not restore it from a stored Pending row. Native reply attempt facts are NeverAttempted, SocketSubmittedWithoutConsumptionProof, and AttemptedUnknown; unknown is never DecidedUnsent or a resend permission. An active write's30-second ceiling does not enlarge the fixed cut budget; the host owner must resolve refusal/release at its established boundary. Do not change a checked handover body after a flush or write after Deactivated.

6. **Original pending identity.** Match original generation/thread/turn/native request to one broker id on same-generation replay. Missing replay is not withdrawal. An actual generation change is a retirement fence, not permission to bind an old native callback to a new generation. Provider re-registration uses its complete Promoted pending cut, never a warm Prepare snapshot. Broker/history Answered cannot be made newly Pending merely because native consumption is unobserved. Exact host native-scope handover applicability remains a source/design coordination closure, not an asserted migration mechanism.

These are the Lead's bounded candidate choices and closure requirements under owner A, not implemented interfaces. Store ownership and host cut budgets remain with their existing owners. A new journal, timeout/recovery path, private process bypass or second broker authority would require a new owner decision; none is selected here.
