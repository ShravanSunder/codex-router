# Router access requirements

These requirements record Shravan's direct decisions in the continuing Router design discussion on 2026-09-16. They supersede conflicting access and receipt assumptions in earlier drafts; model/effort and unrelated accepted work remain governed by their existing sources. Consumers are the owner, agents commissioning persistent sessions, implementers, and readers/reviewers sharing work through a board thread.

| ID | Authorized need and rationale | Authority / priority |
| --- | --- | --- |
| A1 | Callers choose `write-restricted` or `workspace-write` through a Router enum; Router abstracts native permission arguments. Avoid requiring callers to build native policies or permanent per-agent profile files. | Owner: “Write-restricted?”, “Enum”, “I like arguments for this”, “We can abstract this”; authorized, required |
| A2 | Write-restricted agents can write shared temporary scratch and the selected project's `tmp/` and `docs/wip/`; implementers can write their worktree. These work areas allow research, notes, and intermediate artifacts without general source-write access. | Owner: “Also write to project tmp and docs/wip in the project”; authorized, required |
| A3 | Approval behavior follows app-server defaults rather than a separate Router policy. The owner's existing setup uses workspace-write with automatic approval review. Filesystem selection is distinct from approval selection. | Owner: “what app server sets as default”, “I already use workspace write with auto approve”; authorized, required |
| A4 | Sessions launched for one board work thread share scratch keyed by its root message ID, enabling collaboration and continuity. | Owner: “All read only should share scratch pad based on the thread id”, clarified “The message root id to be specific”; authorized, required |
| A5 | Persistent sessions retain their selected access and shared scratch association through resume. The permission abstraction must handle native arguments/restoration without forcing callers to recreate sessions. | Owner's persistent-Sidekick decisions and request to abstract argument handling; authorized, required |
| A6 | Router supplies its exact Control socket exception by default; other permissions and app-server behavior remain unchanged except the explicitly selected filesystem access/work areas. Communication must not depend on repeated socket approvals. | Owner: “we add the router socket by default to config of the router”; authorized, required |
| A7 | Real completed work must yield truthful receipts; native settings unavailable to readback must not be fabricated or make completion falsely fail. | Owner-directed diagnosis and instruction to update the spec and assign implementation; authorized repair of the demonstrated receipt failure, required |

Specification: [Thread model choice, §5a onward](2026-09-15-thread-model-choice.md). Implementation is assigned by the user-facing orchestrator; this document does not authorize upstream Codex changes, global configuration writes, or production process replacement.

Evidence gaps: normal app-server socket enforcement and cold-resume restoration of inline definitions remain unproven. Source and debug-sandbox results are evidence, not substitutes for those runtime obligations. Per-agent subdirectories are a collision-avoidance convention, not a new permissions boundary or concurrency-control service.
